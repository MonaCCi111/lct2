Архитектура интеграции диспетчера – контракт v1

Единый источник правил: api_contract_v1.json, runtime_policy_v1.json,
data/package_manifest.json и data/handoff_v1/schema_manifest.json.
Ни одна продуктовая команда не должна выводить новые пороги из баллов.

1. Два режима данных

Исторический режим читает неизменяемый пакет data с отсечкой
30.06.2026 23:59:59. Он позволяет собрать обзор, карточки, группы,
свидетельства, восемь сценариев таймлайна и графики по сохранённым
свидетельствам. История не содержит настоящих решений диспетчеров.
Из неё нельзя делать вид, будто на 25.09.2026 это текущая телеметрия.

Живой режим начинается с нового потока событий. Бэкенд сохраняет
неизменённые source_event_time, event_id, channel_id, sensor_value,
is_alarm и своё received_at с зоной времени. Дедупликация использует
весь составной ключ этих пяти исходных полей, потому что event_id
переиспользовался. Поздняя запись пересчитывает затронутое окно, но
не стирает ручное решение. Пакетные feature/episode таблицы в data –
исторический вход двух модельных scorers; они не обновляются сами.
Для живого расчёта нужен отдельный процесс, который строит те же
признаки из новых событий, сохраняет последние 72 часа и состояние
эпизодов, проверяет совпадение баллов с пакетным инференсом и только
после этого выпускает новые черновики. Этот процесс ещё не выпущен.

2. Поток данных и владение

Источник -> журнал приёма бэкенда -> ML-расчёт -> версии проекций
каналов, ситуаций, черновиков и групп -> API v2 -> фронтенд.
Бэкенд владеет получением событий, транзакциями, стабильным ID группы,
авторизацией, решениями людей и аудитом. ML владеет признаками,
модельными версиями, выбранными типами, основаниями карточек и
политикой выпуска. Фронтенд владеет навигацией и представлением, но
не рассчитывает баллы, физический ИТС и срочность.

Исторические Parquet – только загрузочный снимок. Для производственной
работы бэкенд может импортировать их в БД, сохранив ID и source_ref.
Большие таблицы и модельные файлы не должны отдаваться браузеру.
Проекции должны хранить calculation_version, available_at и ссылку на
исходные показания. Выпуск новых версий делать атомарным: сначала
загрузка и проверка хэшей, затем смена активной версии API.

3. Навигация и сущности

Обзор -> объект -> группа -> каждый отдельный черновик -> доказательства
-> решение человека. Параллельно объект -> ситуация -> свидетельства.
GET /drafts даёт плоскую очередь с теми же draft_id и review_state, что
деталь группы. GET /objects берёт названия из отдельного справочника
объектов и включает объекты даже без карточек ситуаций.
Каналы и состояние наблюдения доступны независимо от прогноза.
Неизвестный тип получает not_assessed; канал без каталога остаётся
видимым с пустыми object_id/sensor_type и объяснением. Справочник
состояний применяется по типу и точному тексту, конфликт не скрывается.
Числовой ИТС недоступен, its_value = null. Физический инцидент из
дымового, газового или статусного сигнала не подтверждается.

Модельный score имеет смысл лишь внутри model_version. Для
observed_status score = null. В очереди только две активные модели
и два текстовых наблюдаемых статуса. Нет дневного лимита 10.
Группировка не удаляет отдельные черновики. group_id из исторического
ML может измениться при позднем событии; рабочий серверный ID группы
стабилен, а исходный group_id и история изменений сохраняются.

4. Время и воспроизведение

Историческое event_time без зоны и без времени доставки. Не добавлять
к нему +03:00 или Z. available_at – консервативная граница доступности
по событийному времени. Для экрана на момент t показывать только
available_at <= t. Записи с будущим исходом модели доступны лишь в
ретроспективном разборе, не во время проигрывания прошлого.
На фронте исторические source_obs_time и available_at показывать как
буквальную строку с подписью «время источника, зона неизвестна»;
не преобразовывать через браузерный Date и не называть МСК/UTC.
Таймлайн отдаётся страницами по seq; seek пересобирает срез. Решение
в CLI – только симуляция. В API реальное решение хранить отдельно.

5. Решение и наряд

POST /drafts/{draft_id}/decisions требует approved/rejected, непустую
причину и idempotency_key. Автор берётся из сеанса, decided_at ставит
сервер. Повтор того же ключа возвращает прежний результат; попытка
сменить уже принятое решение обычным POST даёт 409. Исправление
ошибочного решения – отдельный POST /decision-corrections с повышенной
ролью, ссылкой на предыдущий decision_id и полным аудитом.

Одобрение черновика само по себе не означает автоматически созданный
наряд. Человек выбирает тип и описание работ и вызывает
POST /work-orders. Бэкенд выдаёт work_order_id, хранит связь с
draft_id; при интеграции с внешней системой отдельно хранит её ID.
GET /work-orders и GET /work-orders/{id} возвращают созданные наряды.
Запись решения не становится меткой физического отказа при обучении.

6. Границы нынешнего выпуска

Пакет достаточен для исторических экранов, восемь фиксированных
сценариев, разборов сохранённых свидетельств и воспроизведения
пакетного скоринга за сохранённые периоды. Он не содержит все 2,6 ГБ
журнала событий: для произвольных исторических графиков за пределами
свидетельств и произвольного объекта/периода replay нужен архив
исходного журнала из локального источника. Для живого режима нужны
источник новых событий и верифицированный инкрементальный ML-расчёт.
Без них нельзя обещать запуск на новых каналах в реальном времени.

7. Приёмка интеграции

Проверить хэши каждого файла, импорт 14 ресурсов и совпадение 12 627
каналов, 11 704 ситуаций, 2 191 черновика, 1 621 группы. Проверить
новый ID известного типа, неизвестный тип, пустой период, повтор и
позднее событие. В API не должно появиться черновиков исследовательских
моделей и массового дыма; источник каждой карточки доступен через
evidence. Проверить восемь сценариев из docs/DEMO_ROUTE_V1.txt,
включая пиковый день 13.03.2026 и ручное решение по draft_id.
Фронтенд и бэкенд подписывают один hash api_contract_v1.json.
