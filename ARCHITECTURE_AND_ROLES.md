## 2. Сквозной пользовательский сценарий (End-to-End)

1. Поступление данных телеметрии:
   - Входной поток телеметрии СМВУ (или пакетный файл за сутки) поступает в серверный шлюз через эндпоинт `POST /api/v1/telemetry/ingest`.
   - Записи нормализуются: булевы значения приводятся к единому виду, числовые показания приводятся к float, очищаются ошибочные заголовки.

2. Расчет признаков и инференс:
   - Модуль генерации признаков рассчитывает для каждого активного датчика динамические метрики: частоту переключений (дребезг) за 1, 6 и 24 часа, долю тревожных сигналов, дисперсию и дрейф температуры/газа, длительность нахождения в текущем статусе.
   - Обученная модель CatBoost оценивает вероятность выхода датчика из строя на горизонте от 24 до 72 часов.
   - Если вероятность превышает порог 0,65, инциденту присваивается статус высокого риска, формируется предиктивное предупреждение с привязкой к объекту, пикету и каналу.

3. Отображение на рабочем месте диспетчера:
   - Фронтенд диспетчера запрашивает сводку через `GET /api/v1/dashboard/summary` и `GET /api/v1/predictions/sensors`.
   - На интерактивной карте коллекторов подсвечивается проблемный участок (например, коллектор «объект Кси», пикет ПК275).
   - Диспетчер кликает на карточку датчика и видит интерактивный график телеметрии: всплески дребезга контактов за последние сутки и прогнозируемую деградацию.

4. Формирование заявки на превентивный ремонт:
   - Сервис автоматически формирует черновик наряда на обслуживание: тип оборудования, регламентные работы (замена датчика, протяжка клемм, калибровка газоанализатора), плановый срок до прогнозируемого отказа.
   - Диспетчер нажимает кнопку «Утвердить наряд» (вызывается `POST /api/v1/tickets`) либо отклоняет рекомендацию с указанием причины (вызывается `POST /api/v1/tickets/feedback`).
   - Событие и решение диспетчера логируются для дальнейшего дообучения модели.

## 3. Контракты межсервисного взаимодействия (REST API)

Все данные передаются в формате JSON. Ответы содержат HTTP-статусы `200 OK`, `201 Created`, `400 Bad Request`, `404 Not Found`, `500 Internal Server Error`.

### 3.1. Получение дерева объектов
- Метод: `GET`
- Эндпоинт: `/api/v1/objects`
- Описание: Возвращает иерархический список объектов, коллекторов и диспетчерских пунктов.
- Пример ответа:
```json
{
  "total": 16,
  "objects": [
    {
      "id": 5327,
      "name": "объект Кси",
      "level": 2,
      "type": "controlHouse",
      "risk_level": "critical",
      "active_sensors_count": 860,
      "failing_sensors_count": 3,
      "sub_objects": [
        {
          "id": 5332,
          "name": "объект Кси ПК0-ПК202",
          "level": 3,
          "piket_from": 0,
          "piket_to": 202
        },
        {
          "id": 5343,
          "name": "объект Кси ПК202-ПК302",
          "level": 3,
          "piket_from": 202,
          "piket_to": 302
        }
      ]
    }
  ]
}
```

### 3.2. Реестр прогнозируемых отказов датчиков
- Метод: `GET`
- Эндпоинт: `/api/v1/predictions/sensors`
- Параметры запроса:
  - `object_id` (int, опционально) – фильтр по объекту;
  - `subsystem` (string, опционально) – фильтр по подсистеме;
  - `min_probability` (float, по умолчанию 0.5) – минимальная вероятность отказа;
  - `horizon_hours` (int, по умолчанию 24) – горизонт прогнозирования.
- Пример ответа:
```json
{
  "total_predictions": 12,
  "generated_at": "2026-09-15T21:00:00Z",
  "items": [
    {
      "prediction_id": "pred-847-228571",
      "channel_id": 228571,
      "sensor_name": "ТЕМП ПК275+9",
      "sensor_type": "Датчик температуры",
      "subsystem": "Температурная подсистема",
      "tag": "847-1.1.44.7.",
      "object_id": 5327,
      "object_name": "объект Кси",
      "piket": "ПК275",
      "failure_probability": 0.89,
      "risk_category": "critical",
      "forecast_horizon_hours": 24,
      "primary_cause": "Аппаратный дребезг контактов (11 788 переключений за 24 ч)",
      "recommended_action": "Протяжка клеммных соединений или замена термопары на ПК275",
      "status": "pending_review"
    }
  ]
}
```

### 3.3. Временной ряд телеметрии датчика (для построения графиков)
- Метод: `GET`
- Эндпоинт: `/api/v1/sensors/{channel_id}/telemetry`
- Параметры запроса:
  - `date_from` (string, формат YYYY-MM-DD);
  - `date_to` (string, формат YYYY-MM-DD);
  - `limit` (int, по умолчанию 1000).
- Пример ответа:
```json
{
  "channel_id": 228571,
  "sensor_name": "ТЕМП ПК275+9",
  "points_count": 5,
  "telemetry": [
    {
      "timestamp": "2026-01-01T00:02:42Z",
      "value_raw": "Неисправен",
      "value_numeric": null,
      "is_alarm": true,
      "is_chatter": true
    },
    {
      "timestamp": "2026-01-01T00:02:44Z",
      "value_raw": "Норма",
      "value_numeric": null,
      "is_alarm": false,
      "is_chatter": true
    }
  ]
}
```

### 3.4. Создание наряда на превентивное обслуживание
- Метод: `POST`
- Эндпоинт: `/api/v1/tickets`
- Тело запроса:
```json
{
  "prediction_id": "pred-847-228571",
  "channel_id": 228571,
  "object_id": 5327,
  "piket": "ПК275",
  "work_type": "Замена датчика температуры",
  "priority": "high",
  "target_completion_hours": 24,
  "comment": "Подтвержден отказ по паттерну дребезга",
  "assigned_brigade": "ЭТР-3"
}
```
- Пример ответа (`201 Created`):
```json
{
  "ticket_id": "TCK-2026-00412",
  "status": "created",
  "created_at": "2026-09-15T21:05:10Z",
  "qr_payload": "https://moscollector.internal/tickets/TCK-2026-00412"
}
```

### 3.5. Пакетная потоковая загрузка телеметрии
- Метод: `POST`
- Эндпоинт: `/api/v1/telemetry/ingest`
- Тело запроса:
```json
{
  "batch_id": "b-20260915-01",
  "records": [
    {
      "event_id": 4524243389,
      "channel_id": 120473,
      "date": "2026-08-01",
      "time": "03:09:27",
      "alarm": false,
      "value": "28"
    }
  ]
}
```
- Пример ответа:
```json
{
  "processed_count": 1,
  "anomalies_detected": 0,
  "inference_duration_ms": 12.4
}
```

### 3.6. Выгрузка аналитических отчетов (PDF / XLSX)
- Эндпоинты:
  - `GET /api/v1/reports/incidents.xlsx` – выгрузка журнала прогнозов и заявок на ТО в формате Microsoft Excel;
  - `GET /api/v1/reports/summary.pdf` – выгрузка сводной справки по надежности коллекторов для руководства.

### 3.7. Интеграция с метеорологическими службами (Open-Meteo)
- Эндпоинт: `GET /api/v1/weather/current`
- Назначение: передача фактических метеоданных города Москвы (температура, влажность, осадки) в модель и на дашборд.

### 3.8. Ролевая модель доступа (RBAC)
- Поддерживаемые роли пользователей через заголовок `X-User-Role`:
  - `dispatcher` – оперативное рабочее место диспетчера ОДС;
  - `supervisor` – аналитический дашборд руководителя эксплуатационного подразделения.

### 4.1. Персональный план-трекер: Слава (Капитан, Data/ML)
1. Подготовка обучающей выборки:
   - Использование среза телеметрии 2024–2026 гг. с временным разделением (Time-Series Split: обучение до конца 2025, валидация на I полугодии 2026 года без перемешивания во времени).
   - Формирование целевой метки $Y \in \{0, 1\}$: возникновение отказа (`Неисправен`, `Обесточен`, `Отключено устройство`) на скользящем окне в следующие 24–72 часа.
2. Фичеинжиниринг:
   - Частота сработок `тревожное == 't'` за окна 1 час, 6 часов, 24 часа, 7 дней;
   - Частота осцилляции/дребезга (смена значений за секунды);
   - Скользящее среднее, стандартное отклонение и тренд для числовых каналов (температура, газ);
   - Категориальные признаки: тип подсистемы, тип датчика, корневой узел (`tag_root`), принадлежность к объекту.
3. Обучение и калибровка моделей:
   - Базовая модель: градиентный бустинг CatBoostClassifier с оптимизацией F-beta (фокус на Precision > 0.70 при Recall > 0.50).
   - Калибровка вероятностей (Isotonic Regression / Platt Scaling) для корректной оценки рисков.
   - Сохранение артефактов модели в формате ONNX / joblib и подготовка пайплайна инференса для Сани.

### 4.2. Персональный план-трекер: Саня (Backend)
1. Каркас сервиса на FastAPI:
   - Настройка модульной структуры приложения: `routers/`, `services/`, `models/`, `schemas/`.
   - Описание Pydantic v2 схем согласно утвержденному контракту REST API.
2. Слой данных:
   - Развертывание PostgreSQL 12+ в docker-compose (`postgres:15-alpine`) как основной СУБД проекта (с поддержкой локального запуска на SQLite через `DATABASE_URL`).
   - Автоматическая накатка схемы и загрузка справочников объектов и каналов при старте контейнера.
   - Модуль генерации отчетов в XLSX (`openpyxl`) и PDF (`reportlab`) для руководства.
   - Интеграция с Open-Meteo API для передачи погодных факторов в модель.
3. Интеграция ML:
   - Загрузка весов обученной модели CatBoost/ONNX в виде синглтона.
   - Реализация фонового скоринга активных каналов (время инференса объекта < 300 секунд).
4. Управление нарядами:
   - Реализация CRUD-эндпоинтов для заявок на ТО/ППР, сохранение решений диспетчера.
5. Контейнеризация:
   - Написание многоэтапного `Dockerfile` и `docker-compose.yml` для гарантированного запуска стенда одной командой `docker compose up --build`.

### 4.3. Персональный план-трекер: Рома (Frontend)
1. Каркас SPA-приложения:
   - Инициализация проекта на React 18 + Vite + Tailwind CSS.
   - Реализация дизайн-системы по брендбуку ЛЦТ 2026 (Montserrat, палитра #FF0053, #1C1D22, #8A83D1).
2. Аналитическая панель диспетчера:
   - Карточки сводного состояния 16 ключевых объектов коллекторного хозяйства;
   - Индикаторы счетчиков: всего каналов под контролем, датчики в зоне высокого риска, количество нарядов на ТО;
   - Переключатель ролей RBAC («Диспетчер ОДС» / «Руководитель подразделения») и кнопка выгрузки отчетов (PDF/XLSX);
   - Информер метеоусловий Москвы (внешний фактор температуры и влажности).
3. Интерактивная схема коллекторов и пикетов:
   - Визуализация линейной трассы коллектора с разметкой по пикетам (ПК) и цветовой подсветкой проблемных зон.
4. Графический модуль временных рядов:
   - Интерактивный график на базе Recharts с отображением истории показаний датчика, порогов нормы и выделением зон дребезга контактов.
5. Журнал предиктивных оповещений и модальное окно наряда:
   - Таблица тревог с сортировкой по вероятности и времени упреждения;
   - Модальное окно подтверждения заявки на ремонт с предзаполненными рекомендациями ИИ и кнопкой отправки в диспетчерский наряд.
