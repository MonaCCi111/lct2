# Единый регламент интеграции и технические соглашения команды Dolos (INTEGRATION_SPEC)

Данный документ фиксирует все технические нюансы, форматы данных, контракты интерфейсов и правила взаимодействия между Славой (ML), Саней (Backend) и Ромой (Frontend). Все решения принимаются как окончательные стандарты разработки для исключения конфликтов на этапе сборки.

---

## 1. Регламент данных и телеметрии (Data Layer)

### 1.1. Формат временных меток (DateTime)
- В сырых CSV дата и время разделены (`дата`: YYYY-MM-DD, `время`: HH:MM:SS).
- В базе данных, на бэкенде и во всех JSON-ответах API используется строго единый стандарт ISO 8601 в часовом поясе Москвы (UTC+3):
  `YYYY-MM-DDTHH:MM:SS+03:00` (например, `2026-01-01T00:02:42+03:00`).
- Сортировка временных рядов на бэкенде выполняется строго по возрастанию временной метки.

### 1.2. Нормализация гетерогенного поля `значение_датчика`
Поле `значение_датчика` на уровне парсера бэкенда и скриптов предобработки ML раскладывается на три независимых атрибута:
1. `raw_value` (string): исходная строка из CSV без изменений (например, `"0.01"`, `"Неисправен"`, `"28"`).
2. `numeric_value` (float или null):
   - Если строка переводится в число (включая замену запятой на точку), записывается float (`0.01`, `28.0`, `25.4`).
   - Если строка является текстовым статусом (`Норма`, `Неисправен`, `Включен`), записывается `null`.
3. `status_code` (enum string):
   - `normal`: нормальная работа (`Норма`, `Движения нет`, `Дыма нет`, `В норме от +3 до +40`, `Есть питание`, `Включен`, `Выключен`);
   - `failure`: аварийные статусы и отказы (`Неисправен`, `Обесточен`, `Затоплен`, `Отключено устройство`, `Много неисправных устройств`, `Батарея неисправна`);
   - `alarm`: технологические тревоги (`Обнаружен дым`, `Обнаружен газ`, `Обнаружено движение`, `Не замкнут`, `Температура ниже 3ºC`);
   - `unknown`: неопределенные состояния (`Неопределен`, `Не определено`).

### 1.3. Унификация булева признака тревоги
- В сырых данных встречаются `t` / `f` и `True` / `False`.
- На уровне ingestion-пайплайна признак приводится к строгому типу boolean:
  - `True`, если значение равно `t`, `true`, `1`, `True`;
  - `False` во всех остальных случаях.

### 1.4. Очистка аномалий и сбросов таймеров
- Строки с повторными заголовками внутри CSV (`дата == 'дата'`) безусловно отбрасываются при чтении.
- Записи с датами сброса часов контроллеров (`1970-01-01`) исключаются из обучающих выборок и хронологических графиков.

### 1.5. Формат хранения данных и обязательный PostgreSQL
- СУБД проекта: в строгом соответствии с разделом 11 ТЗ ДЖКХ основной СУБД является **PostgreSQL 12+** (в `docker-compose.yml` развертывается контейнер `postgres:15-alpine`).
- Подключение на бэкенде: через переменную окружения `DATABASE_URL`:
  - В Docker-окружении (обязательно для жюри): `DATABASE_URL=postgresql+asyncpg://postgres:postgres@db:5432/moscollector`;
  - Локально для автономных тестов разработчиков без Docker: `DATABASE_URL=sqlite+aiosqlite:///./app.db`.
- Реляционные таблицы в PostgreSQL: `objects`, `channels`, `predictions`, `tickets`, `audit_logs`.
- Логи телеметрии для построения графиков: тестовый срез [telemetry_sample_100k.csv](file:///g:/lct2/dataset/representative_slice/telemetry_sample_100k.csv) хранится в формате Parquet (`telemetry_sample.parquet`) для быстрого чтения и фильтрации без накладных расходов на индексы.

## 2. Спецификация стыка ML <–> Backend (ML Interface)

### 2.1. Формализация целевой переменной ($Y$)
- Целевое событие ($Y=1$): переход прибора или узла в отказ (`status_code == 'failure'`: статусы `Неисправен`, `Обесточен`, `Отключено устройство`) на горизонте упреждения от 24 до 72 часов.
- Окно наблюдения для фичей: скользящее окно в 24 часа до текущей точки анализа $t$.
- Окно прогноза: интервал [t + 24 ч, t + 72 ч]. Заглядывание в будущее строго исключено.

### 2.2. Формат артефакта модели и окружение
- Обученная модель сериализуется в формат `.cbm` (нативный формат CatBoost) или `.onnx`.
- Веса сохраняются в директорию `backend/models/catboost_sensor_failure.cbm`.
- Версия Python для запуска: 3.11+.

### 2.3. Программный контракт класса инференса
В репозитории создается файл `backend/app/ml/predictor.py`. Саня вызывает метод `predict_sensor_risk`:

```python
from pydantic import BaseModel
from typing import List, Optional

class SensorRiskInput(BaseModel):
    channel_id: int
    sensor_type: str
    subsystem: str
    tag_root: str
    piket: str
    flapping_count_1h: int
    flapping_count_24h: int
    alarm_ratio_24h: float
    numeric_std_24h: Optional[float] = None
    last_numeric_value: Optional[float] = None
    hours_since_last_alarm: float

class SensorRiskOutput(BaseModel):
    channel_id: int
    failure_probability: float
    risk_category: str  # "low", "medium", "critical"
    forecast_horizon_hours: int  # 24
    primary_cause: str  # Текстовое объяснение фактора риска
    recommended_action: str  # Рекомендация для наряда ТО
```

### 2.4. Заглушка для Сани на старте (DummyPredictor)
До передачи весов от Славы Саня использует класс-заглушку:
- Если `flapping_count_24h > 5` или `alarm_ratio_24h > 0.2`:
  `failure_probability = 0.88`, `risk_category = "critical"`, `primary_cause = "Аппаратный дребезг контактов"`, `recommended_action = "Протяжка клемм и ревизия датчика"`.
- Иначе:
  `failure_probability = 0.08`, `risk_category = "low"`, `primary_cause = "Показания в пределах нормы"`, `recommended_action = "Штатный мониторинг"`.

## 3. Спецификация сетевых контрактов Backend <–> Frontend (REST API)

Все эндпоинты возвращают JSON в кодировке UTF-8.

### 3.1. Даунсэмплинг для графиков телеметрии
- Эндпоинт `GET /api/v1/sensors/{channel_id}/telemetry` возвращает не более 1 000 точек.
- Если за выбранный интервал записей больше 1 000, бэкенд применяет алгоритм выборки ключевых точек:
  - Всегда включаются точки смены статуса (переходы Норма <-> Неисправен <-> Тревога);
  - Для непрерывных числовых рядов берется равномерный шаг усреднения.

### 3.2. Топологическая привязка (Схема вместо GPS)
- Так как точные GPS-координаты подземных тоннелей отсутствуют, объекты и каналы привязываются к линейной схеме коллекторов по пикетам (ПК).
- Модель данных топологии:
  ```json
  {
    "collector_id": 5327,
    "collector_name": "объект Кси",
    "piket_min": 0,
    "piket_max": 302,
    "piket_step_meters": 100,
    "segments": [
      { "name": "ПК0-ПК202", "start": 0, "end": 202, "status": "critical" },
      { "name": "ПК202-ПК302", "start": 202, "end": 302, "status": "normal" }
    ]
  }
  ```

### 3.3. Жизненный цикл заявок на ремонт (Tickets)
Заявки на ТО/ППР имеют фиксированный перечень статусов:
1. `draft`: черновик, автоматически сформированный предиктивной моделью;
2. `approved`: подтвержден диспетчером, наряд передан ремонтной бригаде;
3. `rejected`: отклонен диспетчером как ложная тревога или нецелесообразный выезд (с обязательным комментарием причины);
4. `completed`: работы выполнены, датчик обслужен/заменен.

### 3.4. Формат ошибок API
Все ошибки валидации или выполнения запроса возвращаются по единой схеме:
```json
{
  "error_code": "RESOURCE_NOT_FOUND",
  "message": "Датчик с указанным channel_id не найден в реестре",
  "timestamp": "2026-09-15T21:00:00+03:00"
}
```

### 3.5. Ролевая модель доступа (RBAC)
В заголовках запросов API передается заголовок `X-User-Role`:
- `dispatcher` (Диспетчер ОДС): просмотр карты, анализ графиков, создание и согласование нарядов на ремонт;
- `supervisor` (Руководитель подразделения): просмотр сводных метрик эффективности, подтверждение регламентных планов, выгрузка отчетов.
При отсутствии заголовка по умолчанию выставляется роль `dispatcher`.

### 3.6. Экспорт отчетов руководству (PDF и XLSX)
- Эндпоинт: `GET /api/v1/reports/incidents.xlsx`
  - Возвращает файл Excel с реестром прогнозов, рассчитанными вероятностями, пикетами и статусами нарядов.
  - MIME-тип: `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`.
- Эндпоинт: `GET /api/v1/reports/summary.pdf`
  - Возвращает PDF-справку с ключевыми метриками (число предотвращенных аварий, индекс надежности коллекторов).
  - MIME-тип: `application/pdf`.

### 3.7. Интеграция с метеоданными (Внешний фактор)
- Эндпоинт: `GET /api/v1/weather/current`
- Возвращает актуальные метеоусловия Москвы (температура, влажность, давление, осадки):
```json
{
  "city": "Moscow",
  "temperature_c": 14.2,
  "relative_humidity": 68,
  "surface_pressure_hpa": 1012.5,
  "precipitation_mm": 0.0,
  "source": "Open-Meteo API / cache"
}
```
Данные кэшируются на бэкенде на 1 час и передаются в ML-модуль как внешний контекст.

## 4. Требования к UI/UX и дизайн-системе (Frontend)

### 4.1. Шрифты и оформление
- Базовый шрифт интерфейса: Montserrat (подключается через Google Fonts).
- Базовый размер шрифта: 14px (body), 12px (подписи и метаданные), 18–24px (заголовки).
- Базовое разрешение экрана: строго 1920x1080 (Full HD). Интерфейс должен открываться без горизонтального скролла.

### 4.2. Цветовая палитра по брендбуку ЛЦТ 2026
- Темный фон интерфейса: `#1C1D22`;
- Цвет панелей и карточек: `#252730`;
- Цвет границ и разделителей: `#3A3D4A`;
- Основной акцентный цвет (кнопки, активные элементы): `#FF0053`;
- Вторичный акцент: `#8A83D1`;
- Градиентные заливки графиков: от `#FF0053` до `#310F53`.

### 4.3. Цветовая индикация критичности рисков
- Зеленый (`#10B981`): вероятность отказа < 30% (штатная эксплуатация);
- Желтый (`#F59E0B`): вероятность отказа 30% – 70% (повышенный шум, подозрение на дребезг);
- Красный (`#EF4444`): вероятность отказа > 70% (критическая деградация, требуется наряд на ремонт).

## 5. Инфраструктурный регламент (DevOps / Docker)

### 5.1. Правило запуска в один клик
- Сервис обязан запускаться одной командой:
  ```bash
  docker compose up --build
  ```
- Никаких ручных установок библиотек, создания файлов баз данных или миграций перед запуском. База данных автоматически накатывает схему и начальные справочники при старте контейнера.

### 5.2. Сетевая топология контейнеров
- Порт `80` (или `3000`): фронтенд (Nginx со статикой React SPA);
- Порт `8000`: бэкенд FastAPI (внутренняя сеть Docker);
- Порт `5432`: база данных PostgreSQL 15 (`postgres:15-alpine`) с постоянным томом (volume) `pgdata`;
- Запросы от фронтенда к `/api/` проксируются Nginx на бэкенд, исключая проблемы с CORS в браузере.

### 5.3. Ограничение размера контейнеров
- В Dockerfile запрещено копировать архивы `.7z` и 15 ГБ сырых CSV.
- В контейнер бэкенда монтируется/копируется только готовый файл SQLite (`app.db`), файл тестовой телеметрии `telemetry_sample.parquet` и файл весов модели. Суммарный размер образа не должен превышать 1,2 ГБ.

## 6. Регламент демонстрационного сценария (Demo Storyline)

Для выступления на защите и проверки экспертами в проект закладывается сквозной сценарий демонстрации:

1. **Стартовый экран**: Диспетчер видит сводный дашборд. 15 коллекторов в зеленой зоне, 1 коллектор («объект Кси») подсвечен красным индикатором риска.
2. **Переход к деталям**: Диспетчер кликает на объект Кси. Открывается топологическая схема пикетов. Пикет ПК275 подсвечен красным.
3. **Анализ временного ряда**: При клике на ПК275 открывается карточка датчика температуры `ТЕМП ПК275+9` (канал 228571). На графике наглядно виден аппаратный дребезг (высокочастотная смена статусов Норма/Неисправен) и предупреждение ИИ: `Риск отказа: 89%, Горизонт: 24 часа`.
4. **Формирование наряда**: В один клик диспетчер нажимает кнопку «Сформировать заявку на ТО». Система открывает предзаполненное модальное окно с рекомендацией «Протяжка клеммных соединений на ПК275». Диспетчер подтверждает заявку, статус меняется на «В работе», наряд сохраняется в журнал.
5. **Фиксация эффекта**: Сервис показывает предотвращение аварийного простоя и экономию затрат за счет превентивного выезда вместо ликвидации аварии.

### 4.4. Дополнительные обязательные элементы интерфейса
1. **Переключатель ролей (RBAC)**: В шапке справа размещается селектор ролей «Диспетчер ОДС» / «Руководитель подразделения». При смене роли интерфейс адаптирует доступные вкладки и действия.
2. **Кнопка выгрузки отчетов**: В верхнем меню размещается кнопка «Экспорт отчета» с выпадающим списком форматов (Excel .xlsx / Справка .pdf).
3. **Метеовиджет**: В шапке отображается компактный погодный информер Москвы (температура, влажность, статус осадков), подтверждающий учет внешних факторов.
