Пункт 5 утверждённого плана – ИТС и наблюдаемое состояние

Решение по смыслу показателя:

Числовой ИТС технического состояния 0–100 не выпускается. В данных нет
подтверждённых физических отказов, ремонтов, возраста оборудования,
паспортной шкалы износа и соответствия канала конкретной единице
оборудования. Прогнозы действующих моделей относятся к будущим
эпизодам SCADA, а не к проценту физического ресурса. Сведение баллов
разных моделей, тревог, газа и молчания в одно число не проверяемо.
Справочник состояний охватывает лишь часть типов и не назначает
набор состояний конкретному каналу. Поэтому its_value всегда NULL,
its_status=unavailable, его причина дана явно.

Доступный полезный слой – факты наблюдения. Для каждого канала и конца
месяца сохранены время/значение последнего события, его составной
исходный ключ, последний текстовый статус, число записей за 72 часа,
число явных сообщений «Неисправен» или «Батарея неисправна», число
служебных сообщений и конфликты true/false для одинакового статуса в
одну секунду. Разные статусы с разными флагами в один момент получают
отдельную пометку ambiguous_simultaneous_statuses: это может быть
многофункциональный канал, а не ошибка записи. Сообщение о неисправности
означает только запись прибора,
а не подтверждённый физический отказ. Даже свежая запись не доказывает
исправность. Для событийного датчика отсутствие событий не доказывает
поломку или потерю связи.

Для канала с неизвестным типом используется metadata_missing; без
исторических событий – new_or_never_observed; без записи в последние
72 часа – no_recent_observation; с конфликтом одного и того же статуса
и времени – conflicting_recent_status_flag. Разные статусы с разными
флагами в один момент – ambiguous_simultaneous_statuses. Остальные
получают recent_observation. Эти состояния относятся к доступности наблюдения,
а не к оценке здоровья оборудования. Отдельно указывается, есть ли
последний текстовый статус в справочнике и согласуется ли его флаг
тревоги с источником. Противоречивое или отсутствующее определение
не исправляется автоматически.

Уровни расчёта: канал – наблюдаемые факты; объект и тип датчика –
количество каналов по состояниям и сообщений о неисправности.
Оборудование не рассчитывается, так как в каталоге нет проверенного
оборудования как сущности. На объекте нет среднего балла ИТС.

Запуск из G:\lct2\tmp\publish_ml:

.venv\Scripts\python.exe -m production_ml.pipeline.build_its_evidence_v1 --catalog G:/lct2/dataset/справочник_каналов_датчиков.csv --states G:/lct2/dataset/справочник_состояний.csv --journals production_ml/data/source_v2 --output production_ml/data/its_evidence_v1

.venv\Scripts\python.exe -m production_ml.pipeline.build_its_draft_context --members production_ml/data/dispatch_review_v2/policy_2024/members.parquet production_ml/data/dispatch_review_v2/diagnostic_2025_2026/members.parquet --journals production_ml/data/source_v2 --output production_ml/data/its_evidence_v1/draft_context.parquet

.venv\Scripts\python.exe -m validation.check_its_evidence_v1

channel_history.parquet – по всем известным и новым каналам, один
снимок на конец каждого месяца с января 2024 по июнь 2026. Поля
previous_observation_state и previous_fault_reports_72h позволяют
строить изменение без выдуманного числового индекса.
object_type_history.parquet – агрегаты количества каналов по объекту,
типу и месяцу; физическое состояние объекта не вычисляется.
draft_context.parquet – те же факты за 72 часа на момент каждого
исторического черновика. Это контекст для проверки основания, а не
признак для переобучения старых моделей.

Экран канала должен показывать «ИТС не рассчитан» и точную причину.
Ниже – свежесть телеметрии, последний текстовый статус с датой,
сообщения о неисправности и служебных состояниях, конфликты и ссылки
на исходную запись. Динамику показывать по месяцам. При отсутствии
записей нужен нейтральный вид «нет наблюдения», без зелёного или
красного цвета здоровья. На экране объекта показывать количества по
типам, не средний балл. В карточке черновика показывать факты,
доступные только до времени его создания. Это контракт данных для
будущих фронтенда и бэкенда; на этапе ML интерфейсы не меняются.

После получения графика ППР отдельно объяснять совпавшие служебные
периоды и пересматривать прежние карточки, но график сам по себе не
заменяет журнал подтверждённых ремонтов и не делает балл ИТС
валидным. Время доставки событий не предоставлено. Parquet в Git не
добавлять.
